# OAuth, escolha de provedor e vínculo de contas

## Requisitos reais antes de escolher

O site já tem `User.id`, biblioteca, reviews, senha opcional e OTP. Precisamos autorizar ChatGPT como cliente MCP sem trocar contas, hashes ou login do site por suposição. Cookie de sessão continua uma credencial de navegador; o adaptador aceita access token destinado a ele. Nunca pedir senha/OTP/token ao usuário em tool ou conversa.

O contrato precisa declarar issuer e recurso canônicos, descoberta, PKCE S256, registro cliente, escopos/consentimento, refresh e revogação. A versão [MCP 2026-07-28](https://modelcontextprotocol.io/specification/2026-07-28/basic/authorization) prefere CIMD; DCR é alternativa de compatibilidade, não uma obrigação universal. O resource server publica Protected Resource Metadata RFC 9728; o authorization server publica metadata RFC 8414 ou OIDC discovery. Bearer vai em cada request HTTP; tokens de outro recurso e token em URL são recusados.

Contrato proposto do resource server: issuer em allowlist configurada, assinatura/algoritmo/JWKS verificados, audience correspondente ao URI MCP canônico, exp/nbf válidos, subject não vazio, tipo de access token correto, cliente/grant permitido e consentimento mínimo para a operação. Não aceitar ID token como access token, token de sessão Manifold, role genérica `authenticated` como autorização, `user_id` em argumentos ou metadata editável como prova de conta.

Respostas: 401 + challenge de metadata para credencial ausente/inválida; 403 `insufficient_scope` para consentimento insuficiente; erro de domínio distinto para posse/feature insuficiente. Validar por request e por operação; não ampliar batching além da versão negociada. Evitar singleton/contexto global de usuário e caches compartilhados de dados privados. Chaves podem ter cache com renovação limitada para `kid` desconhecido; falha de validação deve fechar acesso, não fazer fallback anônimo para escrita.

O [guia do host](https://developers.openai.com/plugins/build/auth) documenta PKCE S256, `resource` nas duas etapas e callbacks dependentes do modo/issuer. Copiar URI exata da interface de gestão no futuro; não fixar callback antigo por memória. Com CIMD, ChatGPT documenta `none`/`private_key_jwt`; verificar interseção dos métodos. Não introduzir `client_secret` no navegador ou no modelo.

**Não há vencedor decidido.** Supabase pode ser adequado se consentimento único e restrição por grant local forem aceitáveis, com audience correta demonstrada e acesso a Data API não ampliado. Essa opção não pode fingir granularidade de scopes que o provedor não emite. Auth0 tem documentação mais diretamente alinhada a scopes de API/resource/CIMD, mas exige verificar tenant, grants, métodos, custo/limites e UX do vínculo. Não há evidência de contas/configurações existentes em nenhum.

Alternativa adicional: authorization server próprio usando login atual. Preserva login, porém adiciona responsabilidade por PKCE, descoberta, códigos, clientes, tokens e revogação. **Não recomendar no MVP sem necessidade comprovada.** Uma ponte que emite tokens próprios para esconder incompatibilidades do provedor tem custo semelhante; não é “adaptador simples”. Manter banco Prisma onde está; escolher IdP não obriga migrar DB nem expor tabelas via Data API.

## Vínculo seguro de `iss/sub` com `User.id`

**Proposta de estado mínimo:** registro interno com `(issuer, subject)` único, `user_id`, status ativo/revogado e versão do vínculo. Integridade lógica é verificada no model, conforme repo sem FKs. Subject não se normaliza como email; issuer deve coincidir com o configurado. Aceitar várias identidades para um User apenas por vínculos explícitos; nunca reatribuir par já vinculado a outro User.

1. Após OAuth válido, lookup pelo par. Vínculo ativo resolve User existente; user ausente/revogado não cria fallback. Ler features atuais do banco.
2. Se não houver vínculo, mostrar no navegador “conectar à sua conta Manifold”. Nenhuma biblioteca/review é criada enquanto isso. Não associar automaticamente por email, `email_verified`, username ou metadata do token.
3. Gerar transação de vínculo no servidor, com nonce aleatório, validade curta, uso único, issuer/sub comprovados, sessão/grant iniciador e destino fixo. Levar só referência opaca no link; não colocar token/subject/email em URL.
4. Provar controle da identidade externa em um fluxo OIDC de navegador verificado e correlacionado (state, nonce, PKCE, issuer, audience e subject iguais aos do iniciador). Só apresentar token Bearer em ferramenta não substitui essa etapa de prova/consentimento do navegador.
5. Exigir autenticação recente da conta Manifold alvo. Para conta OTP, verificar novo código no fluxo web existente; senha não é necessária. Mostrar as duas identidades/contas em linguagem compreensível e pedir consentimento explícito de vínculo. Um link encaminhado a outro usuário não pode ligar sua conta à identidade do remetente.
6. Validar CSRF/Origin e sessão de navegador; correlacionar as duas provas à mesma transação, invalidar na troca de conta. Persistir vínculo em operação atômica com unicidade. Conflito concorrente não reatribui identidade.
7. Repetir a resolução após concluir; oferecer desvinculação/recovery autenticados. Desvinculação invalida grants locais e aprovações pendentes ligados ao vínculo. Reconnect mantém o mesmo User; alteração de email não altera associação. Recuperação/swap de issuer exige nova prova explícita, nunca merge automático.

Essa proposta segue a cautela de provar ambas as contas indicada em [account linking Auth0](https://auth0.com/docs/manage-users/user-accounts/user-account-linking), mas é vínculo externo para Manifold, **não** merge de perfis Auth0. Protege contra account takeover por email reciclado/colisão, link encaminhado, sessão trocada e identidade pré-vinculada. Não elimina comprometimento da conta de email usada para OTP; esse é limite do método atual.

Para usuário sem conta Manifold, decidir entre orientar cadastro no site ou criá-la por fluxo dedicado com consentimento e política de ativação. Não inserir automaticamente User com email vindo do token. Plano inicial recomenda cadastro/vínculo explícito para preservar política de domínio.

## Scopes, domínio e revogação

Política proposta: leitura pública sem login; rascunho exige consentimento de escrita; publicação pode exigir scope separado `reviews:publish` se o AS o suportar. Esses nomes são requisitos candidatos, não features existentes. Condição de escrita é **token/grant válido + vínculo ativo + usuário habilitado + feature atual + regras de jogo/posse + aprovação exata**. Não conceder `create:review`, ativar User ou adicionar posse em função de scope.

**PRIVATE, conforme decisão de Pedro:** leitura sem autenticação nunca expõe jogo privado, inclusive por slug/link e recursos relacionados. As tools públicas do MVP permanecem públicas mesmo para usuário conectado. Se houver leitura privada autenticada futura, qualquer scope será apenas limite de consentimento: exigir também vínculo ativo, User atual habilitado e autorização de criador/proprietário ou `read:game:any` do domínio. Não confiar em claim `admin`, email ou membership/afiliação. O repo resolve proprietário pelo estúdio desenvolvedor e não registra autor individual do cadastro; [mapeamento/limitação](01-evidencias.md#private-papeis). Testar token com scope amplo de usuário comum negado e perda de capability/ownership negada na próxima leitura; não criar operação/scope privado nesta rodada.

Desabilitação local deve negar imediatamente novas escritas ao ler features atuais. Revogar o vínculo/grant local bloqueia acessos posteriores independentemente de JWT ainda válido. Logout do site e desconexão do plugin têm semânticas diferentes; não presumir evento de desconexão confiável no host. Pedro decide se revogação só no IdP pode levar até expirar JWT, ou se publicação exige consulta online/grant local revogável sincronizado. No segundo caso, definir fonte de verdade, latency bound e falha fechada; negar publicação se status não puder ser verificado.

Proposta proporcional: access token curto, grant/vínculo local revogável e verificação forte na publicação; não construir plataforma universal de introspection. Um novo token recebido após revogação não deve recriar autorização local automaticamente. IdP logout/revoke, revogação local e conta desabilitada precisam de testes distintos.
